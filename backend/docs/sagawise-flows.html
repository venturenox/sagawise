saga tracker · order_flow example

Sagawise in Motion

Sagawise is a bookkeeper, not a broker. Services exchange real messages over Kafka on their own; separately, they gossip to Sagawise over HTTP — “I published”, “I consumed”, “I failed”. The only thing Sagawise infers by itself is silence: a message published but never consumed in time.

real message (Kafka — invisible to Sagawise) HTTP call to Sagawise reply to an earlier call internal store write failure path / webhook activation — participant is busy for that stretch
STAGE 1

Boot — templates before traffic

Before any order exists, main() runs ParseDSL: every DSL file baked into the image becomes a read-only template in Redis, the search indexes are created, and Postgres gets its archive table. Then the 1-second reaper starts and the server listens on :5000.

STAGE 2

Happy path — one order, two hops

The DSL declares two tasks: order_created (orders → payments, 5 s) and payment_done (payments → shipping, 5 s). Every real Kafka message is bracketed by two reports: the sender announces publish before sending, the receiver announces consume after receiving. Sagawise activates briefly per HTTP call and always replies; each service stays active from the moment work reaches it until it hands the baton on.

STAGE 3

Timeout — when silence speaks

Same start, but payments crashes before consuming. Nobody reports anything — and that nothing is exactly what Sagawise detects. The reaper hands the expired deadline to the same transition script every report goes through: the script checks the task is still PUBLISHED, marks it FAILED, removes the deadline and queues the callback, all in one atomic step, so a last-second consume and the reaper can never both win. A background worker then calls the publisher back so it can compensate, retrying with backoff if the call fails.

STAGE 4

What lives in Redis

Per instance there is one JSON document mutated in place, plus members in three global sorted sets: the deadlines, and the two work queues (archive_pending, webhook_pending) that the transition script fills and background workers drain. No tables, no per-instance keys beyond the doc.

workflow_instance:abc

RedisJSON document — one per saga run, mutated in place

{
  "schema": 2,
  "name": "order_flow",
  "version": "1.0",
  "state": "PENDING → COMPLETED | FAILED",
  "startedAt": 1756400000, "completedAt": 0, "failedAt": 0,
  "tasks": [
    {
      "topic": "order_created",
      "from": "orders", "to": "payments",
      "state": "PENDING → PUBLISHED → …",
      "timeout": 5000,
      "payload": { …stored on publish… },
      "publishedAt": …, "consumedAt": …, "failedAt": 0
    },
    { "topic": "payment_done", … }
  ]
}

Tasks live in the tasks array; the index is the identity. Reports find them in Go by comparing topic (+ consuming service for consume/fail) as plain strings; every state change then runs as one Lua script (transition.lua).

task_deadlines

Sorted set — one global timer wheel for all instances

member          score
──────────────  ─────────────────
abc:0           1756400005000  ← now + timeout (ms)
abc:1           …armed on publish
xyz:0           …other instances too

consume  → script: task COMPLETED + ZREM
expired  → script: task FAILED + ZREM + queue webhook

Both paths run the same script, and Redis runs one script at a time — that is the whole race guard between a late consumer and the reaper. A Redis error leaves the member for the next tick.

The one-sentence model: services do the real work over Kafka; Sagawise just keeps score — clone template, tick tasks forward on gossip, fail them on silence, archive the finished game to Postgres.
