How Sagawise Watches a Saga

Sagawise is a small service that keeps watch over a business action which spans several other services. It notices when one step of that action is never completed. When that happens, it tells the service that started the step, so that service can undo its own work.

This document explains the problem Sagawise solves, what it is and is not, and exactly how it works inside. It needs no prior knowledge of the code. Terms are defined as they appear, and again in the glossary at the end.

Every file and piece of code mentioned here is given with its path, relative to the root of the repository. A reference like backend/instance_engine/reaper.go:44-74 means lines 44 to 73 of that file.

01 The problem Sagawise solves

Large software systems are often split into many small programs called services. Each service does one job and keeps its own data. One service handles orders. Another handles payments. A third handles shipping.

A single business action often needs several of these services to act in turn. Placing an order is a good example. The orders service records the order. The payments service charges the card. The shipping service books a courier. Each step changes data that belongs to a different service.

This creates a problem. There is no single "undo" that covers all three services at once. If the shipping step fails, the order has already been saved and the card has already been charged. Someone has to notice the failure and then reverse the earlier steps.

The standard way to handle this is called a saga. A saga is a sequence of steps across services, where every step has a matching compensating action that undoes it. Charge the card; the compensating action is a refund. Save the order; the compensating action is to cancel it. If a later step fails, the earlier steps run their compensating actions and the system returns to a clean state.

The hard part of a saga is not the undo. It is knowing that a step failed. A service that crashed cannot say so. A message that was lost in transit leaves no trace. Nobody sends a report that says "I never received this". From the outside, a failed step and a slow step look exactly the same: silence.

Sagawise exists to answer one question: did every step of this saga get picked up, or did one of them go silent? When a step goes silent for too long, Sagawise treats it as failed and tells the right service to compensate.

02 What Sagawise is, and is not

The services in a system talk to each other by sending messages. In this project they send them through Kafka. Kafka is a message system that works like a durable mailbox. A service publishes a message to a named channel called a topic. Another service that has subscribed to that topic consumes the message when it is ready. The message waits in Kafka until it is consumed.

Sagawise is not part of that path. It is not a message broker and it does not replace Kafka. It never sees the message content travel. Services keep sending messages to each other exactly as they did before.

Instead, Sagawise listens on a separate channel. After a service publishes a message, it makes one small HTTP call to Sagawise that says, in effect, "I just sent this." After a service consumes a message, it makes another call that says "I just received this." These calls are reports. They carry facts about what happened, not the message itself.

The three services in the diagram are a working example that ships with the repository. Their code is in examples/order_flow/orders/app.js, examples/order_flow/payments/app.js, and examples/order_flow/shipping/app.js. Each one makes its reports through a small helper, examples/order_flow/<service>/sagawiseClient.js.

The picture below shows the two separate paths. The grey band is Kafka, which carries the real messages. The blue band is the HTTP reports that flow to Sagawise.

Sagawise knows only what it is told. It cannot stop a message, delay it, or send it again.

What it can do is this. If a message is sent and nobody reads it within the time limit, Sagawise calls the sending service's error endpoint. The sender can then undo whatever it did. Sections 06 and 07 show how this works.

03 Describing a saga

Before Sagawise can watch a saga, someone must describe it. The description is a small JSON file. Each file describes one workflow, which is the name Sagawise uses for a saga. The files live in backend/sagawise/, one per workflow, and the filename must match the workflow's name field.

Here is the file for the order example used throughout this document, backend/sagawise/order_flow.json, shown in full:

{
  "workflow": {
    "name": "order_flow",
    "version": "1.0",
    "schema_version": "1.0",
    "tasks": [
      { "topic": "order_created", "from": "orders",   "to": "payments", "timeout": 20000 },
      { "topic": "payment_done",  "from": "payments", "to": "shipping", "timeout": 20000 }
    ]
  }
}

A workflow is a list of tasks. One task is one message that must travel from one service to another. Each task has four fields:

  • topic — the name of the Kafka channel the message travels on.
  • from — the service that sends the message.
  • to — the service that must receive it.
  • timeout — how long Sagawise waits for the receive report before it gives up. This is in milliseconds. 20000 means twenty seconds.

The service names in from and to must match a second file, services.json, at the root of the repository. That file lists every service and the web address Sagawise should call when one of that service's tasks fails. The three entries relevant to this example are:

[
  { "service_name": "orders",   "failure_url": "http://orders:4010/v1/sagawise/failure_report" },
  { "service_name": "payments", "failure_url": "http://payments:4011/v1/sagawise/failure_report" },
  { "service_name": "shipping", "failure_url": "http://shipping:4012/v1/sagawise/failure_report" }
]

The workflow files are read once when Sagawise starts and copied into Redis. services.json is read from disk each time a task fails. Both are built into the program's container image, so changing either file means rebuilding the image, not just restarting it.

04 One successful run

Now follow a single order all the way through. Three services take part. Every arrow to Sagawise is one HTTP report.

In words:

  2. orders reports "I sent order_created". Sagawise marks task 0 as PUBLISHED and starts a twenty-second clock for it. Only now does orders actually put the message into Kafka.   3. Kafka delivers the message to payments. Sagawise does not see this. examples/order_flow/payments/app.js:65-80
  4. payments reports "I got order_created". Sagawise marks task 0 as COMPLETED and stops its clock. Then it checks whether every task is complete.   5. payments reports "I sent payment_done". Task 1 becomes PUBLISHED. A new clock starts. examples/order_flow/payments/app.js:45-51
  6. Kafka delivers the message to shipping.
  7. shipping reports "I got payment_done". Task 1 becomes COMPLETED. Sagawise checks again. 05 What Sagawise remembers

Sagawise keeps its working memory in Redis, a fast in-memory data store. It uses a Redis feature that stores whole JSON documents, so each instance is one document.

When Sagawise starts, it reads every workflow file and stores each one in Redis as a template under the key workflow_template:<name>. When a service starts a run, Sagawise copies the template into a new document under workflow_instance:<id>, where the ID is twenty random characters.

backend/templating/templating.go ParseDSL stores the templatesbackend/instance_engine/instance_engine.go StartInstance builds one instance from a template, generateID makes the ID

The document has two parts. The run's own details — its name, its state, when it started and when it ended — sit at the top level under keys like "name" and "state". The tasks are a list under "tasks", in the order the workflow file declares them, and a task is identified by its position in that list. Each task carries its topic, sender, receiver, timeout, state, timestamps and, once it has been sent, a copy of the message that was published. (Before the phase 6 rewrite the tasks were top-level keys named "0", "1", … and the code told them apart from run details by testing whether the key was a number; that layout is gone.)

To find the right task for a report, Sagawise reads the topic and receiver of every task in the list and compares them, in Go, with the values the report carries. The values are compared as plain text; nothing from a report is ever turned into a query, and the saved messages are never looked at. What is compared depends on the kind of report, and the difference matters:

ReportFinds tasks whereWhy
"I sent it" topic matches One message can be meant for several services at once. Every task on that topic is affected.
"I got it" topic matches and to is the reporting service Only the task for this exact receiver is complete. Others on the same topic are still waiting.
"It failed" topic matches and to is the reporting service Same lookup as a receive. Only this one receiver has failed.
backend/instance_engine/instance_engine.go readTaskIdentity reads the topic and receiver of every task; UpdateInstance does the comparison for all three kinds of report

06 Detecting a lost message

This is the heart of Sagawise. Everything so far has been bookkeeping. This section is the one place where Sagawise makes a decision on its own.

The rule is simple. When a task becomes PUBLISHED, a clock starts. If the matching "I got it" report arrives before the clock runs out, the task completes and the clock stops. If the clock runs out first, Sagawise marks the task FAILED.

Why the clock is not kept in memory

The obvious way to build this is to start a timer inside the program for each task. Sagawise used to work that way. It has a serious flaw. If the program restarts for any reason, every timer is lost. Every message in flight at that moment becomes invisible. Sagawise would never notice if one of them was lost.

So the clock is not kept in memory. It is kept in Redis, as a number. Redis has a data structure called a sorted set: a list of entries, each with a numeric score, kept in score order. Sagawise uses one sorted set named task_deadlines. Each entry is one in-flight task, written as <instance id>:<task number>. Its score is the exact moment, in milliseconds, when its clock runs out.

backend/instance_engine/reaper.go:17-21 names the set and builds the entry

The reaper

A background loop called the reaper runs once every second. It asks Redis for the overdue entries (up to a thousand per tick). For each one it asks Redis to run one small script that does the checking and the changing as a single step:

backend/instance_engine/reaper.go StartDeadlineReaper the once-a-second loop, reapExpiredDeadlines what each tick doesbackend/instance_engine/transition.lua the script, action reap

The entry is removed only inside the script that marks the task FAILED, never before it. If the process dies or Redis returns an error while deciding, nothing has changed and the entry is still there on the next tick. Sagawise used to remove the entry first, as a kind of lock, and read the state afterwards; a crash or a Redis hiccup between the two lost the clock for good, and the task stayed PUBLISHED forever.

Two different time units

The timeout in the workflow file and the scores in the sorted set are in milliseconds. The timestamps stored on the instance document — when it started, when each task was published or received — are in seconds. Both units live side by side. Mixing them up is an easy mistake.

backend/instance_engine/instance_engine.go:237 millisecondsbackend/instance_engine/instance_engine.go:133backend/instance_engine/instance_engine.go:76 seconds — every task timestamp is stamped by markTask
A gap that used to be here

Earlier versions read a task's state and wrote the new one as two separate steps, so an "I got it" arriving between them could be overwritten by the reaper's FAILED. Every change now goes through the same script, whether it comes from a report or from the reaper. Redis runs one of the two first; the other sees a task that is no longer PUBLISHED and is refused — a 409 for the report, a dropped entry for the reaper. The same script also ends the run and, when the run fails, removes the clocks of its other tasks, so a run fails once and the sender is called once.

backend/instance_engine/transition.luadocs/contract.md §2–§5 and §10, the rules the script implements

07 Telling the sender

A task can fail in two ways. A service can say so directly, by sending an "it failed" report. Or the reaper can decide it failed because the clock ran out. Both paths run the same transition script, and the script does the first half of the work in one step: it marks the task FAILED, removes its clock, records the time, decides whether the run is now finished, and adds one entry to a second sorted set called webhook_pending.

backend/instance_engine/transition.lua the fail and reap branchesbackend/instance_engine/instance_engine.go UpdateInstance for the reportbackend/instance_engine/reaper.go for the clock

A background worker does the second half. It drains webhook_pending: for each entry it looks up the sender, the receiver and the saved message, and makes an HTTP call to tell the sender what happened. Splitting the work in two matters. The state change is instant and cannot be lost. The call is slow and can fail, so it is retried with growing pauses (2 s, 6 s, 18 s… up to five minutes) for eight attempts, and a slow receiver only delays its own call, never the reaper or anyone else's call. If every attempt fails the entry is dropped, logged and counted; the task and the run stay FAILED regardless.

backend/instance_engine/queue.go the workerbackend/instance_engine/instance_engine.go webhookJob one deliverydocs/contract.md §6 the delivery rules

Which service? Not the one that failed. The one that sent the message.

This surprises most people the first time, but it is the correct choice and it is the core of the saga idea. If payments never received order_created, then payments did nothing and has nothing to undo. But orders already saved an order and sent a message. Orders is the one holding work that now needs to be reversed. So orders gets the call.

Two details make this work. When a service reports "I sent it", it includes a copy of the message body, and Sagawise saves that copy on the task. Later, when the task fails, Sagawise sends that same copy back to the sender. The sender does not need to keep its own record of what it sent.

backend/instance_engine/instance_engine.go UpdateInstance reads the body once and hands it to the script, which saves it at tasks[i].payload; webhookJob reads it back on failure

The address to call comes from services.json at the root of the repository. Sagawise reads that file from disk every time a task fails, looks up the sender's name, and uses the address it finds.

backend/instance_engine/engine.go FileRegistry
An unregistered service stops the program from starting

Every sender named in every workflow file must have an address in services.json. Sagawise checks this once at startup and refuses to run otherwise, so a task can never fail without a sender to call. (If the address were missing anyway, the worker would log and drop the call; the task stays FAILED.)

One message, several receivers

Section 05 noted that an "I sent it" report matches tasks by topic alone. This is what lets one message reach more than one service.

The project's second workflow, backend/sagawise/user_creation.json, has two tasks on the same topic, user_created_saga, going to two different services. One "I sent it" report starts both tasks, together or not at all. Each gets its own clock. Each waits for its own "I got it". One can complete while the other is still waiting; if one of them then times out, the run is FAILED, the other's clock is removed, and the sender is called once.

08 The states a task can be in

Every task moves through a small set of states, and so does every run. They are close to mirror images: a run reaches COMPLETED only when all of its tasks do, but it reaches FAILED the moment any one of them does.

The table below shows what each report does, depending on the task's current state. A 409 means Sagawise refuses the report and tells the caller why, with a stable error code such as TASK_ALREADY_COMPLETED. Once a run has ended, every report on it is refused with INSTANCE_TERMINAL, whatever the task's state.

Every report accepts a flag called is_retry. It exists for the case where a message, or the HTTP report about it, is delivered a second time. With is_retry=true a report that repeats a change already made — "I sent it" for a task already sent, "I got it" for one already received — is answered 200 and changes nothing. There is one exception: repeating "I sent it" while the task is still waiting restarts its clock and replaces the saved message, because the receiver is about to get a fresh copy. The flag never forces a change the table forbids. A task that is COMPLETED or FAILED stays so, and a run that has ended accepts nothing but these harmless repeats. (It used to skip every guard in the table at once; that is what audit finding #2 was about.)

09 Where the code lives

Sagawise is written in Go. The source lives under backend/. Note that the Go module is still named wtfsaga, the project's former name, so imports read wtfsaga/instance_engine rather than sagawise/....

The engine is about 1,900 lines across seven files, one of them a Lua script that Redis runs. Most of the thinking happens in three of them: the script, the report handler, and the queue worker.

FileLinesWhat it does
instance_engine/transition.lua 180 The state machine. Runs inside Redis as one atomic step: checks the task's state, writes the new one, adds or removes the clock, ends the run when it should, and queues the archive and the call to the sender. Every change to a task or a run goes through it, whether it comes from a report or from the reaper.
instance_engine/instance_engine.go 705 Handles every report: checks the parameters, finds the task by comparing topic and receiver in Go, runs the script, answers in JSON. Holds the two jobs the workers run (one archive insert, one call to a sender) and the read-only listing endpoints.
instance_engine/queue.go 220 A worker over a sorted-set queue: claim the entries that are due, run the job, remove the entry on success or push it back with a longer pause on failure. Used twice, for archiving and for calling senders.
instance_engine/reaper.go 102 The sorted set of clocks and the loop that checks it. Short, but it is the only place Sagawise decides anything on its own.
instance_engine/engine.go 204 The Engine struct that owns every dependency (the Redis client, the Postgres pool, the clock, the service registry, the HTTP client, the two workers) and the startup check that every sender has a failure address.
templating/templating.go 216 Runs once at startup. Validates and reads the workflow files into Redis, creates or recreates the search indexes, creates the Postgres table.

Six things worth knowing before changing anything

  • Workflow files and services.json are baked into the container image. Editing either one does nothing until the image is rebuilt with make restart. backend/Dockerfile:33-34Makefile:13-14
  • The Redis search indexes rebuild themselves when their definition changes. Startup stores a hash of each index definition in Redis and drops and recreates the index when the code's definition differs. Changing an index's shape needs no manual step; the documents are kept and re-indexed. backend/templating/templating.go ensureIndex and the two index definitions in ParseDSL
  • Finished runs are copied to Postgres but deliberately left in Redis. Redis stays the live store that every read endpoint queries; Postgres is only the long-term archive. Nothing prunes Redis, so it grows without bound. backend/instance_engine/instance_engine.go archiveJob the archive write, and the comment explaining why nothing is deleted
  • Go never writes a task's state directly. Every change goes through transition.lua, run by Engine.transition. New behaviour that touches state belongs in the script, so that it stays one atomic step; Go only decides which task the report is about and how to phrase the answer. The document layout the script expects is called schema 2; a document from before the rewrite (tasks under "0", "1") is refused with a 500, and a development stack is upgraded with make clean. backend/instance_engine/transition.luabackend/instance_engine/instance_engine.go transition, readTaskIdentitydocs/design-phase-6.md the design and its decisions
  • Every answer is JSON, and every error carries a stable code. requireParams reports every missing parameter at once, so a body reads like {"error":"MISSING_PARAM","message":"missing query parameter(s): action_type, event_name"}. A refusal by the state machine is a 409, an unknown thing a 404, and a Redis or Postgres problem a 500 with the code INTERNAL, never a business answer. backend/instance_engine/instance_engine.go codeStatus, writeErrordocs/contract.md §9
  • Database setup runs only on a first, empty volume. postgres-dev/setup-databases.sh creates one database per entry in POSTGRES_DATABASE_LIST in the root .env, but it does not run again if db_data/ already exists. postgres-dev/setup-databases.sh.env:13 the database listMakefile:16-20 — make clean removes the volume

— Glossary

Short definitions of every term used in this document, in the order a new reader is likely to need them.

service
A small, separately running program that does one job and keeps its own data. Orders, payments, and shipping are each a service.
saga
A business action made of several steps, each in a different service, where every step has a matching undo. If a later step fails, the earlier steps are undone.
compensating action
The undo for one step of a saga. A refund is the compensating action for a charge.
Kafka
A message system that services use to send data to one another. Messages wait in Kafka until a service reads them.
topic
A named channel inside Kafka. A message is sent to a topic, and any service subscribed to that topic can read it.
publish / consume
To send a message to a topic, and to read a message from one. In this document, "I sent it" and "I got it".
report
An HTTP call from a service to Sagawise stating what the service just did. There are three kinds: publish, consume, and fail.
workflow
Sagawise's name for a saga. A JSON file that lists the tasks a saga is made of. Lives in backend/sagawise/.
task
One message that must travel from one service to another. Each task has a topic, a sender, a receiver, and a timeout.
timeout
How long Sagawise waits, in milliseconds, for "I got it" after "I sent it" before treating the task as failed.
instance / run
One live copy of a workflow, tracking one real saga as it happens. Stored as a single JSON document in Redis under the key workflow_instance:<id>.
Redis
A fast in-memory data store. Sagawise keeps all live runs and all clocks here.
sorted set
A Redis data structure: a set of entries, each with a number called a score, kept in score order. Sagawise uses one to store every running clock.
reaper
A background loop that runs once a second, finds overdue clocks, and marks their tasks as failed. Defined in backend/instance_engine/reaper.go. It is the only part of Sagawise that changes anything without being told to.
failure URL
The web address Sagawise calls to tell a service that one of the tasks it sent has failed. Listed per service in services.json at the repository root.
Postgres
A relational database. Sagawise copies each finished run here for long-term storage.
PENDING / PUBLISHED / COMPLETED / FAILED
The four states of a task: not yet sent, sent and waiting, received, and given up on. A run uses PENDING, COMPLETED, and FAILED — it has no PUBLISHED state of its own.
